Antes de empezar

Esta preparación es común a los laboratorios. En Windows usamos exclusivamente Git Bash dentro de Windows Terminal, perfil Workshop - Bash. Los comandos bash de esta guía van en esa terminal. Los bloques text son prompts para Copilot Chat en VS Code, modo Agent. El portal permite leer, copiar y descargar, pero no ejecuta el producto ni certifica lo que declare el agente.

Completa estos cuatro pasos en orden con tu usuario habitual de Windows:

  1. Crear tu carpeta del curso y la terminal Workshop - Bash.
  2. Iniciar sesión en GitHub.
  3. Validar las herramientas con un solo comando.
  4. Crear tu repositorio desde el template y clonarlo.

Necesitas Windows 10 u 11, conexión a internet y Git for Windows, que incluye Git Bash. Para el primer paso abre Git Bash desde el menú Inicio; después usarás Workshop - Bash.

1. Crear tu carpeta del curso y la terminal

Ejecuta el instalador con la opción curso. Este comando pide tu matrícula y tu nombre, crea tu carpeta personal del taller y configura Windows Terminal para abrirla por defecto en el perfil Workshop - Bash. Al terminar, abre una pestaña en esa carpeta; allí clonarás tu repositorio. Conserva cualquier contenido existente.

S1: construir un pedido y comprobar la respuesta

Un prompt reduce ambigüedades y hace explícitas tus decisiones. No garantiza una respuesta correcta. El agente puede leer mal el código, omitir un caso o afirmar que ejecutó una prueba que nunca corrió. Tu trabajo incluye comprobarlo.

Construir un pedido

Usaremos seis partes. Ámbito indica dónde puede actuar; las otras cinco explican qué necesita saber y qué resultado esperas.

ParteQué aportaEjemplo de ai-labs
ÁmbitoDelimita lectura, escritura y rutas relativasCódigo solo en auth/, evidencias generales en raíz, sin tocar código de API ni frontend
ContextoAporta evidencia y decisiones existentesLee el contrato de POST /auth/login, RETO.md y reglas
ObjetivoDefine el resultado buscadoEncontrar cómo se construye la consulta de login
RestriccionesExpresa límites al trabajoNo editar código ni cambiar el contrato
Criterios de aceptaciónPermite contrastar el resultadoCitar archivo y línea, distinguir hipótesis y hallazgo confirmado
Formato de respuestaFacilita consumir y revisar el resultadoTabla con riesgo, evidencia y comprobación pendiente

El diagrama reúne las decisiones antes de enviar el pedido. Contexto no significa pegar todo el repositorio: selecciona archivos que permitan resolver la tarea dentro del ámbito.

Comprobación: en el prompt de abajo señala qué frase limita archivos, cuál aporta contexto y cuál permite refutar la respuesta. Si una frase no tiene una función clara, reescríbela.

Comparar dos pedidos sobre la misma tarea

Pedido ambiguo, para analizar en clase antes de ejecutarlo:

text
Revisa si el login tiene SQL injection.

No dice qué login, qué puede modificar ni qué evidencia necesitas. Puede producir una respuesta genérica o una corrección que no pediste. Mejora el mismo pedido:

text
AMBITO
Workspace ai-labs abierto en su raiz. Lee codigo solo en auth/.
Todas las rutas parten de la raiz. Lee README.md, RETO.md y
docs/ generales. Este pedido es de solo lectura; no escribas archivos.
Git se ejecuta desde la raiz; las pruebas propuestas usan cwd auth/.
No leas ni modifiques codigo de api/ ni web/. Usa IDs H-AUTH-NN y componente auth.

CONTEXTO
ai-labs autentica mediante POST /auth/login. Lee README.md,
RETO.md y docs/ENDPOINTS.md si existe. Localiza la ruta desde el recurso
HTTP hasta la consulta a SQLite. No des por cierta la lista de RETO.md.

OBJETIVO
Determinar si entradas del login llegan concatenadas a una consulta SQL.

RESTRICCIONES
No edites codigo ni ejecutes ataques contra servicios remotos. Usa solo
codigo y datos ficticios locales. Si falta un archivo o no puedes ejecutar
una comprobacion, dilo. No cambies contratos ni leas otros componentes.

CRITERIOS DE ACEPTACION
Identifica el recorrido de la entrada hasta la consulta con archivo y linea.
Distingue concatenacion, parametrizacion y cualquier caso no comprobado.
Propone una prueba local con credenciales validas, invalidas y entrada con
comilla, con resultado esperado segun el contrato observado. No afirmes
que la prueba paso si solo la propusiste.

FORMATO DE RESPUESTA
Tabla: afirmacion | evidencia archivo:linea | comprobado o hipotesis |
prueba propuesta. Termina con preguntas abiertas y comandos no ejecutados.

El objetivo sigue siendo revisar SQL injection en login. Cambió la precisión: el ámbito evita mezclar implementaciones, el contexto dirige la lectura, los límites evitan ediciones prematuras y los criterios exigen una cadena de evidencia. El formato deja visibles las incertidumbres. Pedir evidencia mejora la revisión; no demuestra que las citas sean verdaderas.

Cada paso elimina una ambigüedad distinta. Una respuesta más larga no prueba que el pedido mejoró: debe permitir decidir si la afirmación es correcta.

Actividad: agrega al pedido ambiguo una sola parte cada vez. Antes de enviar, escribe qué suposición deja de ser necesaria. Compara con un compañero qué información sigue faltando. No envíes el pedido ambiguo si el modo Agent tiene permisos de edición amplios.

Comprobar contra código y pruebas

  1. Abre las rutas citadas dentro de auth/. Comprueba las líneas y sigue el dato desde el request hasta la consulta. Una línea con SQL no demuestra por sí sola que sea alcanzable con entrada de usuario.
  2. Lee el contrato observado y separa comportamiento existente de comportamiento deseado. Una prueba de caracterización registra el primero; una prueba de seguridad debe demostrar la corrección, aunque falle antes del cambio.
  3. Ejecuta los comandos de pruebas y cobertura en tu terminal. Compara salida, código de salida y reportes con lo afirmado por el agente.
  4. Revisa git diff main -- auth/ desde la raíz de ai-labs, y revisa las secciones de auth en los documentos generales. Verifica archivos nuevos con git status --short. Confirma que el cambio corrige la causa y que la prueba fallaría ante el defecto original.
  5. Si una afirmación carece de evidencia, mantenla como hipótesis. Registra el límite y formula el siguiente pedido antes de marcar un hallazgo como resuelto.

La revisión devuelve información al prompt. Si un comando falla por el entorno, eso es un resultado de ejecución; no prueba que el código sea correcto ni que el hallazgo esté corregido.

Comprobación: toma una fila de la respuesta. ¿Otra persona puede repetir el comando y localizar las líneas sin preguntarte nada? Señala qué evidencia le falta.

Tu adaptación y su justificación

Elige un componente y una pregunta confirmable del ejercicio. Usa su plantilla, o las de API y frontend.

  • Decide el foco. Por ejemplo, en API: "¿una entrada de nombre de archivo puede salir del directorio de uploads?"; en frontend: "¿se muestra un error cuando el servicio de autenticación no responde?".
