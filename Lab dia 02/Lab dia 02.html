# Skill: Feature Intake -> Spec Checklist

## 1) Metadata
- **Skill ID:** feature-intake-spec-checklist
- **Version:** 0.1.0
- **Purpose:** Estandarizar la definición de funcionalidades antes de la implementación generando un paquete mínimo trazable que cubra alcance, decisiones, riesgos, aceptación y validación.
- **Audience (roles):** Chapter/PO, Tech Lead, Backend, Frontend, QA, Cyber
- **When to use:** Antes de crear tareas de implementación o abrir un PR significativo.
- **When NOT to use:** Incidentes P1 de producción, cambios triviales como typos o tareas sin impacto funcional.
- **Sensitive inputs:** No incluyas datos reales de clientes, credenciales, secretos, tokens ni URLs internas no autorizadas.
- **Expected output:** Markdown estructurado mediante la sección Output a continuación.

## 2) Inputs
Proporciona la información en este formato:

- **Business context (brief):**
- **Feature request / user story:**
- **Expected impact (metric or outcome):**
- **Scope (in/out):**
- **Known technical constraints:** (stack, standards, performance, availability)
- **Known risks:** (security, compliance, stability)
- **Dependencies:** (services, teams, data)
- **Team Definition of Done (DoD):** (if available)

## 3) Output
Devuelve **solo** un documento Markdown con estas secciones y bullets:

1. **Summary**
2. **Scope**
    - Dentro del alcance
    - Fuera del alcance
3. **Supuestos**
4. **Decisiones técnicas por tomar (pendientes o resueltas)**
5. **Riesgos y mitigaciones**
6. **Criterios de aceptación (medibles)**
7. **Plan de validación**
    - Pruebas unitarias
    - Pruebas funcionales
    - Seguridad (comprobaciones mínimas)
    - Evidencia requerida (qué adjuntar)
8. **Tareas sugeridas por rol**
    - Chapter/PO
    - Tech Lead
    - Backend
    - Frontend
    - QA
    - Cyber
9. **Preguntas abiertas**

## 4) Constraints
- No inventes requisitos: si falta información, inclúyela bajo **Preguntas abiertas**.
- No propongas herramientas fuera del stack permitido.
- No incluyas datos sensibles ni secretos.
- Los criterios de aceptación deben ser verificables; no escribas “mejorar el rendimiento” sin una métrica.
- El plan de validación debe incluir al menos un elemento de evidencia concreto, como salida de pruebas, un checklist o un archivo actualizado.
- Mantén la salida en un máximo de 1-2 páginas para que siga siendo usable.

## 5) Validation Rules
La salida es válida si:
- Incluye todas las secciones definidas en Output.
- Tiene al menos 3 criterios de aceptación medibles.
- Tiene al menos 3 tareas para cada rol central: Tech Lead, Backend y QA, o explica por qué un rol no aplica.
- Incluye al menos 2 riesgos con mitigaciones.
- No contiene datos sensibles ni secretos.
- No contiene supuestos no declarados.

## 6) Evidence
Adjunta o referencia estos elementos en el PR o entrega:
- `SKILL.md` versionado.
- `examples/input.sample.md`.
- `examples/output.sample.md`.
- Tag de versión para el Skill, como `skill-feature-intake-v0.1.0`.
Criterio de salida: otro rol debe poder leer el archivo y saber que activa el Skill, que informacion recibe, que devuelve, que limites respeta y como se valida.

Reto final: del log al ticket

Reto final: del log al ticket con Skill y MCP

Quién prepara cada cosa

El MCP del portal entrega los logs, las reglas y el contrato, y el portal genera un token personal para conectarte. Tú creas el Skill y revisas su resultado. No tienes que desarrollar ni ejecutar el servidor, programar una API bancaria ni subir archivos a GitHub.

Caso 1. La transferencia no confirma su resultado

Una persona realiza una transferencia. La aplicación queda esperando y el equipo de soporte necesita saber qué ocurrió antes de indicar al cliente que vuelva a intentarlo.

Log: caso-01-transferencias.log, texto con pares clave/valor. Se obtiene con obtener_caso y caso-01.

El Skill debe localizar la operación con errores, agrupar los reintentos, descartar la copia de un evento y ocultar los datos sensibles. Debe distinguir un tiempo de espera agotado de una transferencia rechazada o completada. El ticket debe explicar qué confirmación falta y qué revisar antes de recomendar otro intento.

Comprobación del participante: las líneas de una transferencia exitosa diferente no deben mezclarse con la incidencia. El informe no puede afirmar que se perdió dinero ni que la transferencia falló definitivamente.

Caso 2. El cliente no puede entrar a su banca digital

Soporte recibe un reclamo de acceso. Necesita distinguir un problema del servicio de identidad de un rechazo por credenciales incorrectas.

El Skill debe interpretar este formato, identificar la dependencia que falla, conservar el código HTTP relevante y eliminar las credenciales ficticias de los extractos. Debe aplicar el mismo contrato de salida que en los otros casos.

Comprobación del participante: el rechazo por credenciales de otra operación no pertenece a esta incidencia. El ticket no debe afirmar que la contraseña del cliente es incorrecta ni que todos los usuarios están afectados.

Caso 3. Aparece una alerta de posible cargo duplicado

El sistema de tarjetas detecta dos movimientos asociados a un mismo pago. Operaciones necesita evidencia para conciliar antes de decidir si corresponde una devolución.

Log: caso-03-cargos.log, texto con pares clave/valor. Se obtiene con obtener_caso y caso-03.

El Skill debe relacionar la alerta con los movimientos de la misma operación, distinguir un evento repetido de dos movimientos distintos y conservar sus identificadores técnicos. La evidencia debe ocultar el dato de tarjeta y explicar qué resultado de conciliación falta.

Comprobación del participante: el ticket describe una posible duplicidad, no una devolución aprobada. Copiar dos veces la misma alerta no equivale a dos incidentes.
